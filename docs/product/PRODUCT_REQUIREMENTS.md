# Catnip Forge：探索 MVP Product Truth

状态：已确认产品需求。来源：用户 2026-09-07 完整施工指令。只记录产品要求，不记录实现进度或把实现假设定稿。新增决定必须由用户确认；普通实现选择记入施工文档。

## 1. 产品与用户

产品名 Catnip Forge；中文定位“Catnip 硬件智能开发平台”；英文定位 Autonomous Hardware Development Agent。它是面向 ESP32 / ESP32-S3 等硬件开发的本地 Electron 桌面 AI IDE，不是知乎搜索客户端。本次增加社区知识驱动的探索能力，不重做产品。

现有价值链：自然语言需求 → Catnip Agent → Skills → Runtime MCP → ESP-IDF 工程 → 修改源码 → Build → Flash → Serial → 读取真实开发板反馈 → 判断运行结果。

MVP 第一用户是手持 ESP32 开发板的 Maker / 创客：有模糊创意，或工程可编译/烧录但运行异常，需要真实开发经验和实际修复。功能优先级：找灵感 > 解问题 > OAuth 个性化（OAuth 不在 MVP）。演示尽量覆盖两条链路，解问题是更重要黄金 Demo，具体故障需实测选择，优先运行异常，不以 header not found 为主。

新增模块统一叫“探索”，在仓库、监视器、任务管理器、编辑器旁出现。首页只有“找灵感”“解问题”，不做“知乎页面”或搜索框首页。另有用户确认的第六个可见工作区“Neil 的 skill 小站”，在内置浏览器中打开固定 Skill Hub，用既有 Skill Manager 完成下载安装；它不是第二套 Skill 系统，也不恢复录制控件。延续现有设计系统，不复活隐藏 workbench。

### 当前工作工程与未完成工作

应用每次冷启动进入主要工作区前，用户必须明确选择一个现有硬件工程，或在应用解析出的 `hardboard/projects` 根目录下创建新工程。可以显示上次选择作为建议，但不得自动激活项目列表第一项、上次 Runtime 工程或其他历史目录。没有当前工程时，Explore 分析、Agent 工程任务、Build、Flash、工程编辑等项目相关动作不得静默落到旧目录。

当前工程是仓库/编辑器、监视器与任务证据、任务管理器、Explore Context/Handoff、Agent 工程执行共同使用的唯一工程上下文。切换工程必须是显式动作；正在执行项目任务时不得无提示切换。全局 Skills、参考资料和本地知识库仍可跨工程访问，不因工程边界复制第二套系统。

选择或切换当前工程时，仓库树、编辑器打开文件与未保存提示、Build/Flash/Serial 的目标和事件过滤、Agent 会话列表/当前会话/持续上下文必须作为同一工程会话原子切换。不得显示或注入其他工程的 Agent 对话，也不得把已排队、正在构建或正在烧录的任务静默改绑到新工程。迁移期历史全局 Agent 对话只能隔离为未归属数据，不能自动进入任一工程；用户已明确删除此类记录后，当前 UI 不得重新展示或重建“未归属·只读”入口。

找灵感与解问题的未完成工作按“当前工程 + 模式”分别保存。返回探索首页、切换右侧工作区、Renderer reload 或应用重启不得自动清空输入、Context 选择、分析结果、来源、选定 Idea、Plan/Handoff 与阶段；用户必须能继续查看或明确新建/清除。运行中的请求按 requestId 继续归属原工程；若进程重启后无法继续，显示“已中断，可重试”，不得永久假装仍在运行，也不得把结果归到新工程。

每个工程必须拥有可枚举的 Explore 历史目录；“找灵感”和“解问题”分别保存多次使用记录，而不只是各保留一个最新状态。每次记录包含草稿、所选 Context、结构化结果、来源、计划/交接、状态和安全时间元数据；已完成、未完成与中断记录都可恢复。目录和索引必须由 Main 管理并原子写入，不保存 Secret、未选 Context 或无界原始输出。

工程开发 Agent 的对话记录与持续上下文必须统一保存在对应工程目录的受控 `.catnip/agent/` 下；切换工程即切换该工程的 Agent 历史。Explore 使用独立于左侧工程开发 Agent 的 AI 对话记录，每条灵感或问题历史分别保存自己的草稿、对话和四阶段状态，不得占用或污染左侧 Agent 对话。

即使已生成最终交接材料或已经确认提交，所属 Explore 对话、结构化结果和阶段状态仍须保存在对应历史中，可从探索首页恢复查看。用户主动收藏来源时可保存受限的来源会话快照；删除收藏与删除 Explore 历史互不级联，二者均须由用户明确触发。

探索四阶段必须可以回看已到达步骤。第三阶段由 Explore AI 在当前工程的 `.catnip/handoffs/<sessionId>/` 下生成分层的计划和交接材料；第四阶段先展示从工程目录读取的交接材料，只有用户明确确认提交后才交给左侧工程 Agent 执行。工程内 `.catnip` 至少区分 `agent`、`explore`、`handoffs` 子目录，不得把文件平铺堆放在工程根目录。

## 2. 知识来源与职责

社区知识 → Catnip 理解与判断 → 用户确认 → 现有 Agent 执行 → 真实硬件验证 → 用户自己的已验证经验。

必须使用官方 `zhihu` 标准目录型 Skill 和既有 Skill Manager，保留 support files。MVP 使用知乎搜索、全网搜索；不自动扩展热榜、直答、本人 Context、OAuth、官方知识库 API、额度页面。高级用户可在现有 Chat 显式 `@zhihu`；普通用户不需要了解 Skill、CLI、MCP。

不自行重写知乎 HTTP、鉴权、时间戳、错误处理，不从 Renderer 直调知乎，不把搜索放入 Hardboard Runtime。

## 3. 找灵感

用户先表达“我想做什么”，如“有陪伴感的桌面设备”；硬件是自动读取的约束，不先要求复杂硬件表单。Catnip 理解目标并动态生成多个搜索方向，不把关键词组织交给用户，也不写死搜索模板。知乎社区搜索为主，必要时补充全网权威来源。

结果以若干可实现 Idea 为主：是什么、为什么值得做、大致实现方向、与当前工程/硬件匹配程度、知乎依据、必要外部依据。不能把十条搜索结果当最终主体。原始来源保留标题、作者（若提供）、摘要/相关片段、原始 URL；无来源不能声称“知乎用户普遍认为”。

用户选 Idea 点击“开始这个项目”，形成结构化 Idea Context：原始目标、项目/硬件约束、选定 Idea、关键社区与外部依据、建议第一阶段目标。交给现有 Catnip Agent 后只生成执行计划，等待确认，再允许修改/Build/Flash/验证。

## 4. 解问题

入口：探索首页主动进入；或从监视器、Build/Flash/失败任务、当前工程提供“分析这个问题”，不能写“用知乎分析”。

默认自动收集最小必要上下文：芯片/target、当前工程、相关源码、最近一次 Build 结果、最近串口日志、Hardboard 状态。用户能看到使用了哪些 Context 并取消项目。不能扫描整个仓库、build 目录或全部串口历史，也不要求用户先整理所有日志。

默认同时用知乎搜索与全网搜索。知乎提供实践经验，外部资料优先官方芯片/SDK/框架文档。当前工程证据 + 运行证据 + 社区经验 + 权威资料交叉判断，形成可验证假设，不能复制单个回答直接修改。

结果以 Catnip 对当前工程的判断为主：问题、优先验证原因及理由、工程/日志证据、支持判断的知乎经验、外部交叉证据、建议验证步骤。区分社区经验和已证明事实，保留来源冲突，所有原始来源可追溯。

“交给 Catnip”形成结构化 Investigation Context：问题、环境、工程、硬件/target、Build/Serial 观察、社区与全网证据、优先假设、建议执行路径。交接进入现有任务体系：已导入 → 计划中 → 等待确认 → 执行中 → 验证中 → 已解决/未解决。内部 enum 自主设计，但不得新增平行 Task Manager。

## 5. 确认与验证

Explore 阶段仅分析；Handoff 先计划，用户确认前不得修改工程或 Build/Flash。确认后进入修改 → Build → Flash → Serial → 实际验证。

| 声明 | 必要证据 |
| --- | --- |
| 代码完成 | 真实文件改动 |
| 编译成功 | 真实 `hardboard.idf_build` 成功结果 |
| 烧录成功 | 真实 `hardboard.idf_flash` 成功结果 |
| 运行正常 | 真实 `serial_read/wait/capture` 或用户可观察行为 |

无硬件时记录 `REAL_HARDWARE_VALIDATION_PENDING`，模拟不是实机。验证失败保留原假设、测试方式、失败证据、排除结果，再验证下一假设，不掩盖失败。

## 6. 本地个人硬件知识库

Catnip 自己的长期本地知识库，不使用知乎官方 Knowledge Base 作为主存储。用户主动收藏高价值经验，保存来源类型、标题、作者、原 URL、任务相关摘要、标签、可选备注、关联项目、收藏时间、验证状态。不默认保存全文，不批量同步或镜像知乎。

至少有未验证、已验证有效、已验证无效。记录有效/无效的关联项目与真实验证证据；Build 成功不等于经验有效。方案实测失败可记无效或保留明确失败验证记录。

跨项目、跨重启保留。后续任务自动发现相关历史知识卡，先显示“发现相关历史经验”，由用户决定加入；拒绝加入的卡片不得进入分析或 Agent Context。自动发现不等于自动注入。

## 7. Secret 与连接

每个用户用自己的知乎开放平台 Access Secret；无团队统一 Secret、无新云服务。优先官方系统凭证存储；Secret 不进源码/配置/.env 提交、Renderer、日志、URL、Agent 最终输出、截图、视频或安装包。

首次相关使用能表达“连接知乎开放平台”，不直接显示底层 missing/AUTH_REQUIRED。安装初始化遵循官方 SKILL.md：先 Skill 自己的 `scripts/run.* status`，不信任 PATH 裸 CLI；需要安装/升级时先取得授权；真实联调需要 Secret 时再请求，安全传入、不回显、不无意义耗额。不为 MVP 初始化主动读取本人内容或 OAuth 画像。

缺失官方源文件必须记 `OFFICIAL_ZHIHU_SKILL_SOURCE_MISSING` 并索取真实包，不凭提示重建。

## 8. 明确不做

不做 OAuth 关注/收藏/创作与自动画像、热榜独立页、直答核心排障、官方 Knowledge Base 主存储、大规模同步、新云后端/微服务、Web 化、第二套 Agent/Skill/Task、重写 Runtime/Hardboard、无关重构、社交/排行榜/Feed/社区发布/账号体系、embedding pipeline、未来 MCU 泛化。保留当前技术与桌面交付。

## 9. 完成定义

探索两个入口可用；找灵感有真实官方来源、Idea、现有 Agent 计划交接；排障有可取消的最小 Context、两类搜索交叉判断、确认门禁、真实修改/Build/Flash/Serial 结果；知识主动收藏、持久化、相关发现经用户同意加入、真实验证反馈；官方 Skill 完整集成且 Secret 不泄露；既有功能回归通过；Windows 桌面包及冷启动实测；有 baseline、远程备份、阶段提交、明确远端状态和完整接力文档。

缺少真实搜索、硬件或成品证据，不能宣称 MVP 完成。比赛交付包含软件包、环境说明、可完成核心流程的 App，用户制作演示视频。

## 10. 2026-09-11 已确认的产品呈现

- 当前公开版本为 `v2.0.0`，Build `7201`；工作区依次包含仓库、监视器、任务管理器、编辑器、探索、Neil 的 skill 小站。
- 吉祥物和独立软件使用助手统一命名为“Neil·Bauman's 学院呱呱”，使用用户指定形象；助手知识覆盖探索、Skill 小站和现有软件能力，顶部提供经 Main 固定白名单打开的作者 GitHub 入口。
- 新手引导必须介绍探索的独立历史与四阶段门禁、Neil 的 skill 小站及学院呱呱。找灵感/解问题入口采用同系列学院呱呱插画并保持 HTML 文本、键盘焦点和响应式可访问性。
- 第三步生成的 `PLAN.md` / `HANDOFF.md` 可在第四步编辑保存，并可打开其工程目录；只有明确确认提交才进入工程 Agent。

## 11. 2026-09-12 模型与连接管理

- 产品提供独立“模型”工作区，集中管理供应商、模型档案、用途默认值和安全凭据状态；它复用既有 Agent，不产生第二套执行系统。
- 工程 Agent 聊天框可以从已启用、用途兼容的模型中显式选择。选择按工程和会话保存，并在任务创建时冻结；不得在失败或模型删除后静默切换到其他付费模型。
- 首批行为兼容当前 DeepSeek 默认配置；其他供应商只有在对应协议完成真实适配和验证后才标记可用于工程 Agent。
- 知乎已连接后仍可进入“管理连接”，支持重新检查、替换 Access Secret 和退出本机登录；继续复用官方 `zhihu` Skill，不修改 vendor 协议。
- 所有 API Key 和 Access Secret 由 Main/宿主安全输入与系统凭据存储维护，Renderer 只看到是否已配置等元数据。

## 12. 2026-09-13 启动与显示性能

- 发布版前端资源保持本地随包交付，不依赖远程 CSS、JavaScript 或图片；开发模式的本机实时编译不能被当作发布版加载路径。
- 启动动画期间应在隐藏主窗口中完成首屏必要的脚本执行、字体和关键图片解码，再显示可交互界面；必须有有界兜底，不能永久停在启动页。
- 非首屏工作区按需加载；图片按透明度选择 JPEG、WebP 或 PNG，并在不改变内容和清晰度底线的前提下降低解码与传输字节。
- 不把打包资源复制到用户数据目录制造第二份缓存，不引入 Service Worker/CDN，也不预加载所有页面造成启动竞争。

## 13. 2026-09-13 Claude Code 供应商切换纠偏

- 用户人工验收否决第 11 节中“工程 Agent 按工程/会话选择模型”的呈现和运行逻辑；第 11 节保留为历史需求证据，本节为当前有效口径。
- 产品实际执行器是应用内的 Claude Code CLI。“模型”工作区只管理 Claude Code 兼容供应商及其主模型、Haiku、Sonnet、Opus 映射，并提供应用级唯一“当前启用供应商”。
- Chat 不再提供按会话模型下拉，只显示当前启用的 Claude Code 供应商和主模型；切换影响随后创建的任务，运行中和已经入队的任务继续使用创建时冻结的供应商快照。
- Base URL 和模型映射可同步到应用专用 Claude 配置；API Key 仍只保存在系统安全凭据中并由 Main 注入 CLI 进程，不写入普通 Claude settings、Renderer、Chat、日志或任务快照。
- 首批只实现 CC Switch 中 Claude Code CLI 的供应商切换语义，不引入 Codex、Gemini、MCP、提示词、代理、用量统计、导入导出或其他 CC Switch 功能。
