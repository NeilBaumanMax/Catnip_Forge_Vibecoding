# 开发闭环流程整改施工文档

更新日期：2026-08-06
施工分支：`qwen_vision_attachments`

## 1. 目标

恢复并固化 Catnip Forge 的完整开发范式：

```text
现状检查
→ 施工文档
→ 编码
→ 专项测试
→ 失败修复
→ 完整回归
→ 人工或成品验收
→ 文档收尾
→ 精确提交
→ 推送
→ 远端确认
```

任何结构性功能、跨模块修改、发布变更和高风险修复都必须经过这条链路。测试通过、已经提交或生成了安装包，均不能单独代表交付完成。

## 2. 阶段门禁

### A. 开工与基线

- 动态检查当前分支、工作区、上游、远端和相对远端的提交差异。
- 阅读 `HANDOFF.md`、`ARCHITECTURE.md`、`DEVELOPMENT.md` 和相关专项施工文档。
- 识别并保护用户已有改动、密钥、运行态文件和构建产物。

### B. 施工文档先行

- 编码前新建或更新一份匹配本任务的 `*_CONSTRUCTION.md`。
- 写清目标、非目标、架构边界、文件范围、风险、分阶段施工、测试策略和完成标准。
- 施工文档应先形成独立文档提交。紧急修复无法提前提交时，也必须先在工作区写好方案，再改代码，并在日志中说明例外原因。
- 未定义验收标准，不进入编码。

### C. 编码与专项测试

- 按施工文档范围实施，不顺手扩张任务。
- 先运行最贴近改动的专项测试。
- 测试失败时记录根因，修改后重新执行失败项；不能只报告最后一次成功。

### D. 完整回归与验收

- 至少执行 Runtime/Electron 类型检查、主进程构建、Renderer 构建和 `git diff --check`。
- 根据改动执行对应的 `verify:*`、smoke、Windows 打包和发布校验。
- UI、真实 API、真实硬件或客户环境行为不能由静态检查冒充；无法执行时必须明确列为未验收边界。
- 验收记录必须包含日期、代码提交或待提交工作区、命令、结果、人工环境以及未覆盖项。

### E. 文档收尾

- 更新专项施工文档的落地结果。
- 检查 `README.md`、`INDEX.md`、`ARCHITECTURE.md`、`HANDOFF.md`、`DEV_PROGRESS.md`、`LOG.md` 和发布检查表。
- 当前事实与历史记录分开，禁止把旧版本验证写成当前版本已通过。

### F. Git 交付

- 使用明确文件列表精确暂存，禁止 `git add -A`。
- 提交前检查工作区、忽略规则、敏感文件和 `git diff --cached --check`。
- 推送当前施工分支，不未经合并验收直接推入 `main`。
- 推送后查询远端分支并核对远端提交号；只有远端确认成功才称为“已交付”。
- 如果用户明确要求暂不推送，记录为一次任务级例外；该例外不得自动延续到后续任务。
